# TW-728 Part 2 evidence: GeoLibre v3.5.2 geo viewer for the data portal

Prepared by Twistor Holdings LLC

Ticket: TW-728 (reporter Justynn). Branch: `sofia/tw-728-geolibre` in the
twistor-data-portal repo, based on main `f91340c`. No merge performed;
merging is Justynn's word.

## What was wired

- `geo/index.html`: portal-styled wrapper page. It embeds the GeoLibre app
  in an iframe in read-only viewer mode (`layout=viewer&welcome=0&theme=light`)
  and points it at the CLIMATESHIFT-1 layer through GeoLibre's documented
  `data=` deep link. It also links a full-screen viewer and a self-contained
  project variant (below), and carries a static five-site list as a no-JS
  fallback. Linked from the CLIMATESHIFT-1 dataset page hero.
- `geo/app/`: the GeoLibre web app, built from the official v3.5.2 source
  with the upstream embed build (`npm run build:embed`) and committed
  as-is, including the MIT license text at `geo/app/GEOLIBRE-LICENSE.txt`.
  Asset paths are relative, so it serves from any subpath.
- `geo/data/climateshift-1-hemp.geojson`: 30 features, one per real
  CLIMATESHIFT-1 v1 hemp trial record, generated by
  `geo/tools/build_geojson.py` from the actual lbt-os seed
  (`backend/app/data_layer/science/crop_climate/seed.py`, TW-599,
  `seed_hemp_records()`, deterministic). Every property value is the
  record's own. The seed names locations rather than coordinates, so each
  feature's geometry is the documented city coordinate of its named site
  (Burlington VT, Corvallis OR, Columbia MO, Ithaca NY, Fort Collins CO;
  6 records each). The file and the page both state this plainly, and the
  records stay labeled `synthetic: true`, matching the portal.
- `geo/data/climateshift-1-project.geolibre.json`: the same records as a
  self-contained GeoLibre project (format 0.2.0): blank basemap, layer
  embedded inline, project view centered on the continental US. Loads
  with no tile service at all. Generated by the same script.

## Deep-link contract findings (from the v3.5.2 source)

- `data=` values must be absolute http(s) URLs. The parser
  (`dataUrlParameters` / `httpUrl` in `src/lib/data-url.ts`) silently
  drops relative URLs. The wrapper therefore resolves the layer URL
  against its own origin in script. First version of the wrapper used a
  relative URL and loaded no layer; the server log proved the app never
  fetched the file. Fixed and re-verified. The log is committed at
  `docs/tw728/server-access.log`: its first app-shell request carries the
  relative `data=` URL with no GeoJSON fetch after it, followed by the
  corrected absolute-URL runs.
- The `data=` loader waits for the map API, which is handed over on the
  basemap's `style.load`. If the basemap style cannot load, the layer
  load never starts. The `?url=` project route does not have this
  dependency when the project carries a blank basemap.

## Honest limits

1. **Bundle size is the headline limit.** 201 MB of app in this branch is
   proof-grade, not production-grade. Recommendation for merge time:
   merge the wrapper, data, and tools (a few hundred KB) into the portal,
   and deploy `geo/app/` as its own static artifact (for example a
   `geo.twistor.co` subdomain or a release asset the wrapper points at).
   That call is Justynn's; this branch keeps everything together so the
   proof runs anywhere with one static server.
2. **Sandbox browser networking blocked the full visual proof of the
   `data=` route.** This sandbox's Chromium cannot reach any external
   host (verified directly: example.com fails with and without the
   sandbox proxy), so GeoLibre's default remote basemap style and tiles
   never load here, the `data=` loader never gets its `style.load`, and
   point glyphs never painted in any capture (pixel-checked: zero).
   What is proven here is the wiring end to end except final paint on a
   live basemap: file serving, deep-link parsing (source-verified),
   project fetch, layer registration, and view application. One eyeball
   pass on a networked machine, or post-merge on the live portal, closes
   the last step. The offline project route exists on the page precisely
   so the layer can be checked with no tile service.
3. **Points stack.** Six records share each city coordinate, so a site
   shows one stacked point; the viewer's identify shows one record at a
   time. Real per-plot coordinates would come from a future dataset
   version, not from this seed.
4. **First load is heavy.** The full GeoLibre app (analysis tools,
   DuckDB, Cesium) ships in the embed; a viewer-only production build or
   the separate-deploy route in item 1 is the fix path.
5. **Mobile view.** Per the standing rule (browser-first, complete
   touch-friendly mobile view): the wrapper is responsive (viewer height
   70vh under 640px, full-screen link offered) and GeoLibre's viewer
   layout is touch-capable, but this was verified by code and layout
   inspection only, not on a physical device.
